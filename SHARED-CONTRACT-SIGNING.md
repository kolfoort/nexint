Shared MCNDA and JVA signing
===========================

Deployment order
----------------
1. Apply `supabase/migrations/20261105150000_uploaded_joint_contracts.sql`, then
   `supabase/migrations/20261105151000_uploaded_contract_nexora_identity.sql`.
2. Deploy `mcnda-bundle` and `signing-confirmation` Edge functions.
3. Deploy the static website changes.

The migration is transactional and fails closed if the existing function bodies
do not match the expected anchors. It stores their previous definitions in a
private, revoked backup table. Existing PDFs, versions, signatures, party access,
MFA, OTP and company-authority rules remain unchanged.

Preparation
-----------
Use the shared MCNDA/JVA workspace. Select a new agreement, choose own MCNDA or
JVA PDF, enter its exact reference and upload the complete reviewed execution
copy. Select every required company representative through their company role.
The administrator must confirm the uploaded content and review the server-stored
PDF before release. The original PDF bytes are stored privately and hashed on
the server; standard clauses are not appended. The final server bundle appends
execution evidence only, preserving the accepted source pages.

MCNDA and JVA require separate agreement threads. A new revision requires a new
upload and fresh consent. Each counterparty signs using its own authenticated
account and document-bound email confirmation. Nexora signs last. Preparing a
private draft does not send notifications; release queues the signing invitations.
SMTP acceptance does not prove receipt or reading.

Do not release PDFs labelled draft/review/not for signature or documents with
unresolved required party/authority fields. Uploading a PDF does not certify
company registration or authority evidence. Review the correct final documents
and their link/hash references before release.

Validation
----------
Install the pinned development dependencies, then run `npm run test:signing`.
The in-memory PostgreSQL tests execute the actual migration against an isolated
legacy signing-action fixture. Identity/profile infrastructure is stubbed; its
existing production checks are retained by the migration and must additionally
be checked in the deployed portal. No production signatures are generated by
these tests. The UI tests exercise consent invalidation and upload requirements;
the PDF tests verify exact-byte preservation and malformed-input rejection.
